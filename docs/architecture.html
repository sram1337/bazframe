Engineering / Bazframe 2

Bazframe
architecture

Bazframe composes standard Skills and personal instructions into profiles, then projects the selected profile into a coding agent. This guide describes the code that acquires, stores, selects, and applies those resources.

Source snapshot · 8adaf2c 0.1.0-beta.3 Public support · macOS / Linux

Self-contained page; no external assets. Source links open files relative to this repository checkout. Product design remains authoritative as the implementation changes.

01

Overview

Bazframe is a local, filesystem-backed application with CLI, TUI, and Pi extension entry points. CLI and TUI operations manage state. The installed Pi extension consumes that state at startup and reload.

Logical responsibilities, not a strict import-layer diagram. The CLI calls domain functions directly. The shipped Pi artifact contains its own supported-platform readers; it does not simply call the CLI or TUI service.

Separate operations: acquisition changes which resources are available; membership changes what a profile includes; selection changes which profile is active; projection determines which resources and instructions a runtime receives.
02

Callers & consumers

Start with the entry point for the operation. The CLI, TUI, and Pi extension have distinct dispatch paths rather than a single shared controller.

Management / scripting

The CLI is the dispatcher

src/cli.ts passes argv to runCli() and sets the process exit code. parseArgv() produces typed commands, help, version, or usage errors.

Dispatch applies the platform check, composes application effects, arranges applicable lifecycle recovery, then calls the domain operation. Presentation turns results into human text or one JSON document.

Consumers: interactive users, shell automation, integration tests. Both installed executable names target dist/cli.js.

Interactive management

The TUI uses typed methods

runTui() constructs BazframeTuiService and renders TuiApp. Ink and React load only after CLI dispatch to tui.

The service returns DashboardSnapshot data and calls shared profile/resource functions. state.ts owns navigation, selection, layout, and display helpers—not filesystem transactions.

Boundary: no CLI subprocesses. Profile actions, individual membership, editors, and consent-bound library addition form the current writable UI surface; Settings and Adapters are read-only.

Runtime integration

Pi loads an owned artifact

installPiAdapter() installs artifacts/pi/bazframe.ts into Pi's global extension directory. Users then launch pi directly.

The extension resolves policy and the active profile, contributes skillPaths, appends instructions, and implements /bazframe info and /bazframe reload.

Boundary: Pi owns tools, models, trust, native resources, and execution. The deprecated bazframe pi launcher is a separate path, not the primary adapter architecture.

03

The object model

All Skills use the Agent Skills format. Bazframe manages their ownership, membership, snapshots, and runtime selection.

Added Skill → live bytes

The (default) catalog registers one canonical source directory. Profile memberships point directly to the same target, rather than through the catalog link. Local source owners retain the bytes; remote Git sources use Bazframe-managed checkouts.

Library → prepared snapshot

An already-prepared directory, with no build declaration. Its entire root becomes an immutable snapshot. A profile references the whole library; runtime reads use the activated snapshot, not mutable source input.

Package → built snapshot

A source project with an exact bazframe-package.json. Explicit build intent produces an artifact. Bazframe snapshots the entire artifact root and discovers Skills under its declared Skills root.

Stored profile

AGENTS.md + individual Skills + typed whole-library/package references. Managed sharing adds a local identity/publication sidecar. Rename preserves identity; duplicate creates a new profile identity and clears publication linkage.

Ordinary collection references follow a global record's activated digest. Imported resources have stable identities and may use qualified display selectors only when collisions require them.

Effective harness

A resolved runtime view, not another profile to persist. Project overrides take precedence over global policy; absent global policy means enabled. When enabled, Pi's native layers and the selected personal profile contribute to the session.

Instruction contents remain opaque. Bazframe preserves their text and supplier provenance; it does not reconcile contradictory prose or promise semantic precedence.

Collision handling. Inside profile composition, duplicate names reject activation or withhold whole conflicting collections; stored resources are not renamed. At Pi's existing Skill-command boundary, Bazframe can project one deterministic -x-bazframe alias into its runtime cache. An occupied alias is a visible projection failure.
04

Trace an operation

Concrete call paths, with the point at which state changes.

Attach an added Skill to a profile MEMBERSHIP WRITE
profile skill add --profile personal review→addProfileSkill()→profiles/personal/skills/review
  1. Parse the command and select the target.

    CLI dispatch distinguishes explicit --profile from active-profile shorthand. The TUI calls addMembership(profileId, skill) with an explicit target.

  2. Choose ordinary membership or imported identity.

    Ordinary added Skills use addProfileSkill() and readDefaultSkillRegistration(). Imported selectors resolve through mutateImportedProfileResourceMembership(), using stable resource identities instead of catalog links.

  3. Validate and publish only the membership.

    The ordinary path takes the global state lock before the profile membership lock, verifies the expected registration and source, and publishes the parallel link. Existing foreign or mismatched entries are refused rather than replaced.

  4. Consume at the next runtime discovery.

    Pi loads the profile's Skill directories at startup/reload. Full Skill validation belongs at the runtime loader boundary; adding membership does not execute the Skill.

Changed: the target profile's membership. Unchanged: source content, global active selection, and every other profile.
Activate a library update or package build SNAPSHOT + RECORD WRITE
updateLibrary() / buildPackage()→prepare*→validate dependents→activate digest
  1. Enter the shared collection lifecycle under the global lock.

    Collection lifecycle validates the record and canonical source identity. Remote updates first enter managed Git orchestration, which composes the collection engine with checkout/provenance changes.

  2. Prepare immutable input.

    prepareLibrary() copies prepared bytes without executing code. preparePackage() validates the manifest and authorized build, runs literal argv, then snapshots the declared artifact through publishSkillSnapshot().

  3. Validate the candidate and every referencing profile.

    validateProspectiveSkillCollection() checks composition against the reference index. Duplicate Skill names, invalid definitions, or an uncertain reference index block activation.

  4. Revalidate, then replace the descriptor.

    Recheck the source, declaration, previous descriptor, and reference index immediately before publication. The new immutable snapshot exists before the global record changes to its digest.

Consumers read the snapshot identified by the activated record. Failed activation preserves the previous digest; it does not roll back arbitrary source changes made by an unsandboxed build.
Start Pi with the active profile READ + RUNTIME PROJECTION
pi→installed extension→resolveState()→skillPaths + systemPrompt
  1. Pi calls the installed extension's handlers.

    session_start and resources_discover resolve state for their current cwd. The supported default path uses readers authored in this artifact; it does not spawn Bazframe commands.

  2. Resolve policy before loading the active profile.

    Global policy applies everywhere; a canonical Git worktree may supply an override. Effective disable retains native Pi behavior and bypasses profile loading. Enabled sessions read selection, instructions, direct Skills, imported resources, and referenced snapshots.

  3. Validate composition and project command collisions.

    prepareProfileSkillPaths() checks existing Pi Skill commands. A free original name is retained; a collision may create a wrapper under adapter-cache/pi/skill-aliases/. resources_discover returns the resulting Skill paths.

  4. Append instruction sections before the agent starts.

    before_agent_start uses systemPromptOptions.contextFiles. Nonempty means append the profile only. Empty means restore available global Pi context, then append the profile. The incoming prompt and instruction bodies are preserved.

Pi consumes projected resources; authored profiles are unchanged. Alias wrappers are runtime cache writes. /bazframe reload awaits Pi's reload; it is not a background file watcher.
Move a profile to another installation CAPTURE / TRANSPORT / MATERIALIZE
captureProfile()→ZIP or GitHub→materializeCapturedProfile()→candidate swap
  1. Capture a portable, bounded resource closure.

    captureProfile() produces canonical manifest bytes, content-addressed blobs, and an exact preview. It captures ready artifacts without builds. Remote resources remain exact references unless bundled; machine-local identities, paths, and publication linkage are not transport identity.

  2. Write a ZIP or publish exact Git history.

    exportManagedProfile() uses ZIP I/O. publishManagedProfile() uses the GitHub transport with expected-old leases and durable publication intent. On macOS/Linux, publishSidecarCandidate() preserves authored content by copying the profile into a candidate, updating its sidecar, and swapping directories through publication's own journaled sequence. The internal Windows effect updates only the sidecar while retaining the profile root.

  3. Inspect, authorize, and materialize at the destination.

    inspectProfileImport() performs no Bazframe-home mutation. Real import resolves collisions and explicit overwrite consent, then materializes Skills, libraries, and package artifacts. Uncached remote packages may require a report and build consent; exact healthy cached resources can be reused offline.

  4. Activate the imported candidate through the shared transaction engine.

    executeProfileCandidateSwap(), the journal, and recovery reconcile old/candidate/final state. When ownership cannot be proved, the operation retains the affected state and reports the ambiguity.

ZIP imports are independent; Git imports retain a canonical origin for update/version operations. New imports do not become active automatically. Dry-run may use private retained OS-temp Git workspaces, but never builds, logs in, or recovers/mutates Bazframe home.

State & ownership

The managed home is resolved from absolute BAZFRAME_HOME, otherwise ~/.bazframe. Project overrides are also stored here, outside the worktree. This is a representative layout; transaction staging/retained siblings vary by operation and platform.

<BAZFRAME_HOME>/
├── active-profile                       # selected profile ID, not JSON
├── global.json                          # optional disabled policy
├── profile-favorites.json                # TUI preferences, separate from selection
├── projects/<hash>.json                  # canonical Git-worktree policy
├── profiles/<id>/
│   ├── AGENTS.md                         # personal instruction text
│   ├── skills/<skill>                    # physical Skill or managed membership link
│   ├── libraries/<id>.json              # whole-library reference
│   ├── packages/<id>.json               # whole-package reference
│   └── .bazframe-profile-state.json      # optional local identity/import/publication state
├── skills/<skill>                        # (default) live-source registration
├── libraries/<id>.json                  # canonical source root + activated digest
├── packages/<id>.json                   # also artifactRoot and skillsRoot
├── skill-snapshots/sha256/<digest>/
│   ├── manifest.json
│   └── artifact/                        # immutable prepared collection bytes
├── providers/git/
│   ├── checkouts/<kind>/<id>/           # stable managed source paths
│   ├── records/<kind>/<id>.json         # exact remote/revision provenance
│   └── staging/ + recovery/
├── profile-publishing/
│   ├── blobs/ + trees/                  # captured/imported content-addressed store
│   ├── transactions/ + operation-locks/
│   └── staging/ + github-workspaces/    # private operation state
├── adapters/pi.json                     # ownership manifest, not the extension
├── adapter-cache/pi/skill-aliases/       # runtime-generated wrappers
└── locks/                               # cooperating-writer coordination

Three different byte locations

Source: live Skill content or library/package input.
Collection snapshot: an activated prepared artifact under skill-snapshots.
Sharing store: imported/captured blobs and trees under profile-publishing.

Do not treat those stores as interchangeable or require a mutable source to exist before consuming a healthy immutable artifact.

Adapter installation location

<PI_CODING_AGENT_DIR>/extensions/bazframe.ts is the installed extension. Default agent directory: ~/.pi/agent. Bazframe's home stores ownership metadata and runtime cache, not Pi settings or repository instructions.

Internal Windows installation additionally binds runtime code through bazframe/runtime.json in the Pi agent directory. The runtime binding is checked before shared services are imported.

Retained state. Managed profile removal detaches the named non-active profile and retains private state. Ambiguous transactions and process-exposed workspaces may also remain. Snapshot GC and a general workspace-reclamation subsystem are deferred; do not infer “unused” means safe to recursively delete.

08

Code conventions

The implementation uses these patterns and product rules.

TypeScript ESM, explicit dependencies

package.json declares ESM; relative TypeScript imports use emitted .js paths. Options/dependencies carry filesystem, process, clock/test hooks, and platform services as needed. Missing optional effects commonly select Node/POSIX defaults.

Keep decisions in shared engines

*Services and *Effects describe operation-specific interfaces. win32-* supplies concrete effects while common lifecycle/resolver code retains product semantics. Construction or a UI selection is not proof that a later write is authorized.

Exact schemas and identities

Records have explicit schema versions and exact fields. IDs are validated, not silently normalized. A library and package may share a name because identity includes kind. Imported display qualification is derived; stable membership identity is stored separately.

Separate inspection from mutation

Resolvers and status readers do not acquire sources, update libraries, or build packages. Remote work and build execution require explicit lifecycle intent. Adding a catalog object does not add a profile reference; explicit profile targeting does not change selection.

Publish only after validation

Use the applicable lock, expected identity, bounded stable reads, candidate preparation, and revalidation before effects. Single state files use atomic replacement; multi-step profile operations use journals/candidate reconciliation. Preserve ambiguous or malformed state instead of guessing a repair.

Consent is operation-specific

--yes accepts routine confirmations and safe suffix choices, never overwrite/discard. Package build reports bind authorization to exact inputs and literal argv. --force has narrowly defined meanings for profile removal and owned adapter repair.

Presentation is a boundary

Use singular noun-verb commands. Sharing commands emit schema-v2 success/refusal/error results with mutation effects; unrelated JSON remains v1. Human color is separate. status attention is successful JSON with exit 3, not a mutation failure.

Preserve Agent Skills compatibility

Pi's public loader is authoritative on the supported runtime path; internal Windows physical reads preserve the loader contract. No inter-Skill dependency schema is inferred from prose or metadata. Packs, child subsets, and snapshot GC require separate product decisions.

Platform boundary: shared decisions, distinct effects

Windows implementations compose the same product engines with native filesystem effects.

Node implementation

Node / macOS / Linux

defaultApplicationServices supplies Node path behavior; optional domain service dependencies fall back to their supported-platform effects. Managed added-Skill memberships use absolute symlinks.

Portable Node operations still have disclosed final-pathname races against non-cooperating writers. Locks coordinate Bazframe processes; they do not make arbitrary external writes impossible.

Windows implementation

Windows x64 / local NTFS

createWindowsApplicationServices() lazily shares one native backend identity across policy, profiles, resources, Git, adapter, and editor services. Each mutation acquires fresh authority; the backend object is not a cached permission token.

core/win32-native.ts validates the native contract. native/win32/src/ implements identity, privacy, stable reads, locks, junctions, and publication primitives through the packaged N-API addon.

shared lifecycle function→operation Services / Effects→win32 implementation→native backend

Entrypoint routing. assertBazframePlatformSupported() currently refuses Windows command effects; help/version remain available. The default Pi entry point gates before binding I/O, package import, native initialization, or state reads. Internal test entry points exercise composition separately from default dispatch.

Host/source tests and foundation/product CI receipts cover narrower workloads than the full installed-product matrix required before npm publication. See the Windows requirements. Windows Terminal, representative SSH, ambiguous-width rendering, and manual assistive-technology evidence also remain separate TUI gates.

Where to start a change

Start with the requirement, caller, and domain function for the behavior you want to change. Then check its effect implementations and consumers.

  1. Establish the contract. Start with docs/design.md; follow sharing, Pi context, or TUI design for the relevant operation.

    For transaction implementation detail, use profile-publishing-engineering.md. Historical designs do not override the current product contract.

  2. Find the caller and its result shape. Read parse-argv.ts → the matching run-cli.ts branch, or BazframeTuiService → the relevant domain function.

    For runtime behavior, start at the handlers in the actual Pi artifact, not at the deprecated launcher.

  3. Check effect implementations and their consumers. Inspect the operation's Services/Effects, default implementation, and Windows implementation if affected.

    A resource-composition change may affect CLI listings, status, TUI, imported-resource projection, and the installed Pi reader. Shared names alone do not prove behavioral parity.

  4. Run tests for the affected behavior. test/unit/ is organized by source domain; test/integration/ checks connected CLI operations and state changes.

    pi-artifact.test.ts exercises the shipped extension. tui-cli-state-agreement.test.ts checks shared state behavior. test-real-pi.mjs, test-pack.mjs, and terminal scripts test distinct installed/runtime boundaries.

  5. Edit authored inputs, not build output. scripts/build.mjs compiles src/ to dist/ and copies skills/bazframe/ and skills/bazify/ to dist/skills/.

    artifacts/pi/bazframe.ts is authored source despite its directory name. Native release artifacts have a separate admission path. No install-time acquisition or membership mutation is part of the build.

Validation should match the change

npm run check:quick
npm run test:unit -- test/unit/<affected-domain>/<test>.test.ts
npm run build
npm run test:integration -- test/integration/<affected-journey>.test.ts

Use disposable Bazframe/Pi homes, never the user's live ~/.bazframe. Preserve original failures and run focused affected checks. Native qualification and commit, push, tag, or npm publication require authorization. See CONTRIBUTING.md and docs/releasing.md.
